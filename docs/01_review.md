# 기존 자료 검토 의견과 보완 사항

검토 대상: `_original/` 폴더의 제작지시서, 로컬 시제품 코드, 기존 화면 예시, GitHub·Supabase 설치 가이드, 클라우드 코드 초안
검토일: 2026-11-23
전제: 사용자는 가족 5명 안팎, 민감정보 없음, 보안보다 **단순하게 동작하는 것**이 우선, 사용자 식별용 로그인은 필요

---

## 1. 한 줄 결론

기존 자료는 **가족 5명 규모에 비해 지나치게 무겁게 설계**됐습니다. Cognito, Lambda, DynamoDB, 별도 관리자 비밀번호, 1회용 초대 토큰과 실패 복구가 모두 들어가 있습니다. 그 결과 2일 동안 작성한 코드가 서로 연결되지 않은 채 "배포 금지" 상태로 남았습니다.
**Supabase 하나 + GitHub Pages 하나**로 줄이면 같은 목적(가족별 로그인, 목록 공유, 역할 권한)을 지금 바로 배포 가능한 형태로 만들 수 있습니다. 이번에 작성한 코드는 이 방향을 따릅니다.

## 2. 구조에 관한 보완 (가장 중요)

### 2.1 Cognito + Lambda + DynamoDB → Supabase Auth만 사용

| 항목 | 기존 설계 | 문제 | 변경안 |
|---|---|---|---|
| 아이디 로그인 | Cognito 사용자 풀 + Supabase 서드파티 인증 연동 | AWS 계정·결제수단 필요, 서비스 2곳 운영, Lambda 배포 필요 | 아이디를 내부적으로 `아이디@설정도메인` 이메일로 바꿔 Supabase Auth에 저장합니다. 사용자는 아이디만 입력하고, 이메일은 보내지 않습니다(이메일 확인 끔). |
| 가입 제한 | 관리자가 1회용·48시간 초대를 발급하고 DynamoDB로 사용 처리 | 초안은 가입 실패 시에도 초대가 소모되는 결함이 있음(지시서 14절에서 스스로 지적) | **가족 공용 가입 코드** 하나를 DB에 두고, 가입 시 DB 트리거가 검사합니다. 코드가 틀리면 계정 자체가 만들어지지 않으므로 "초대 소모" 문제가 없습니다. 코드는 관리자가 SQL 한 줄로 바꿉니다. |
| 관리자 | 앱 안에 "별도 관리자 비밀번호 + 15분 관리자 모드 + 전역 목록 접근" | 구현·시험 부담이 가장 큼. 5명 가족에게는 필요성이 낮음 | **Supabase 대시보드 = 관리자 콘솔**입니다. 비밀번호 재설정, 가입 코드 변경, 계정 삭제는 대시보드 SQL Editor에서 미리 준비된 SQL로 처리합니다(`supabase/admin.sql`). 앱에는 관리자 화면을 두지 않습니다. |
| 관리자 본인 복구 | 콘솔 재설정 + 별도 관리자 인증정보 재설정 | 별도 관리자 비밀번호가 없어지므로 이 절차도 필요 없음 | Supabase 계정(GitHub 로그인 등)만 지키면 됩니다. |

> ⚠️ **확인이 필요한 한 가지:** Supabase가 가짜 이메일 도메인을 어떤 기준으로 거부하는지 공식 문서에서 확인하지 못했습니다. `a@a.com`, `@example.com`이 `email_address_invalid`로 거부됐다는 사용자 보고가 있습니다. 그래서 도메인을 `config.js`의 `EMAIL_DOMAIN`으로 빼 두었고, 설치 가이드 6단계에서 첫 가입으로 먼저 시험하도록 했습니다. **가족이 가입한 뒤에는 이 값을 바꾸면 안 됩니다**(기존 계정으로 로그인할 수 없게 됨).

### 2.2 목록 초대: 1회용 토큰 → 아이디로 바로 추가

- 가족은 모두 계정이 있고 서로 아이디를 압니다. 초대 코드를 만들어 카톡으로 보내고, 받은 사람이 붙여 넣게 할 필요가 없습니다.
- Owner/Co-owner가 **멤버 관리 창에서 가족 목록 중 사람을 골라 역할과 함께 추가**하면 끝납니다.
- 이렇게 하면 지시서 5.2절의 만료, 재사용, 동시 수락, 발급자 강등, 취소 검증이 **모두 필요 없어집니다**. 테스트 항목도 크게 줄어듭니다.
- 권한표(Owner/Co-owner/Member/Guest)는 그대로 유지하고 서버(DB 함수)가 검사합니다.

### 2.3 동시 수정: 완료 체크는 충돌이 나지 않게

- 기존 설계는 목록 전체를 버전 번호와 함께 저장합니다. 그래서 **둘이 장을 보며 동시에 체크하면 한 명은 계속 "충돌" 오류**를 보게 됩니다. 가족 사용에서 가장 흔한 상황입니다.
- 변경안:
  - 완료 체크는 전용 함수 `checklist_toggle`로 **그 항목 하나만** 바꿉니다. 버전을 올리지 않으므로 충돌이 생기지 않습니다.
  - 편집(항목 추가·이름 변경·이동 등)은 기존처럼 버전으로 충돌을 감지합니다. 저장할 때 서버는 **완료 상태를 DB 값으로 유지**하므로, 편집자가 다른 사람의 체크를 덮어쓰지 않습니다.
  - 편집 충돌이 나면 최신 내용을 다시 불러오고 "다시 시도해 달라"고 안내합니다. 모든 동작이 즉시 저장되므로 잃는 것은 마지막 동작 하나뿐입니다.
- 지시서 7.2절의 "미저장 내용 다운로드"는 즉시 저장 방식에서는 의미가 거의 없어 제외했습니다.

### 2.4 실시간 반영

실시간 구독은 하지 않고, **화면을 다시 볼 때(탭 전환·앱 복귀)와 30초마다** 최신 상태를 불러옵니다. 편집 중이거나 대화상자가 열려 있으면 건너뜁니다. 5명 규모에서는 이것으로 충분합니다.

## 3. 기존 화면 코드(`checklist-local-test.html`)의 문제

| # | 문제 | 영향 | 조치 |
|---|---|---|---|
| 1 | 같은 이벤트(click/submit/change)에 핸들러가 여러 번 등록되고, `stopImmediatePropagation`과 capture 단계로 서로를 가로챔 | 유지보수가 매우 어렵고, 기능을 추가할 때 어느 핸들러가 실행될지 예측하기 어려움 | 이벤트 처리를 하나의 함수로 정리해 새로 작성 |
| 2 | `#batchCat`, `#batchSub` 등 존재하지 않는 요소를 참조하는 옛 코드가 남아 있음 | 지금은 다른 핸들러가 먼저 가로채서 우연히 동작함 | 제거 |
| 3 | `addHistory`, `history` 필드, "항목 상세·이력" 화면 등 이력 기능의 흔적이 남아 있음 | 지시서는 "이력 기능 없음"으로 정했으므로 서로 맞지 않음 | 제거 |
| 4 | HTML5 드래그앤드롭만 지원 | **휴대폰(터치)에서는 ☰ 드래그가 작동하지 않음**. 가족은 대부분 휴대폰으로 사용 | 드래그를 **포인터 이벤트 방식으로 새로 작성**해 PC와 휴대폰 모두 ☰ 를 끌어 이동합니다. 터치 기기에서는 손잡이를 40px로 키우고, 끌 때 화면 끝 자동 스크롤, 끌고 있는 항목 표시, 삽입 위치 선을 보여 줍니다. 멀리 옮길 때 쓰도록 **"선택 항목 이동" 대화상자**도 함께 둡니다 |
| 5 | 검색어를 입력할 때마다 전체 화면을 다시 그리고 포커스를 복원함 | 휴대폰 한글 입력(조합 중) 때 글자가 끊길 수 있음 | 검색 결과 영역만 다시 그림 |
| 6 | 복제 시 `confirm()`의 확인/취소로 "마감일 비우기/유지"를 고름 | 무엇을 눌러야 할지 헷갈림 | 복제 대화상자에 체크박스로 표시 |

## 4. 로컬 시제품(`server.py`, `index.html`)

- Python 서버 + SQLite 구조라 GitHub Pages나 Supabase에 올릴 수 없습니다. **이번 배포에는 쓰지 않습니다.**
- 비밀번호 해싱, 시도 제한, 세션 처리 자체는 잘 만들어졌습니다. 하지만 Supabase Auth가 같은 일을 대신하므로 옮겨 올 부분이 없습니다.

## 5. 클라우드 SQL 초안(`001_checklist.sql`)

좋은 점(이번 코드에 반영함):
- 데이터를 비공개 스키마에 두고 `security definer` 함수로만 접근하게 한 구조
- 목록 단위 `version`, `for update` 잠금으로 마지막 Owner 보호
- `validate()`의 구조 검사(카테고리·서브카테고리 참조, Simple 금지 필드, 날짜 형식)

보완한 점:
- `user_id()`가 Cognito 발급자를 검사함 → `auth.uid()`로 교체
- 담당자(`assignees`)의 형식 검사가 없고, "새 담당자는 참여자여야 한다" 규칙(지시서 7.1)도 없음 → 추가
- Member가 `save`로 완료 상태를 바꾸는 방식이라 동시 체크 충돌이 남 → `toggle` 함수로 분리
- 참여자 추가(아이디로), 스스로 나가기, 가족 목록 조회, 표시 이름 변경 함수 추가
- 함수 실행 권한의 `revoke`/`grant`가 함수마다 길게 나열돼 있어 빠뜨리기 쉬움 → 반복문으로 일괄 처리

## 6. 설치 가이드의 문제

- 두 가이드 모두 "배포하지 마시오"로 끝나서 **실제로 따라 할 수 있는 단계가 없습니다**. → `docs/02_setup-guide.md`에서 처음부터 배포까지 순서대로 다시 작성했습니다.
- 다음 사항이 빠져 있었습니다. 모두 새 가이드에 넣었습니다.
  - Supabase **Confirm email 끄기**: 켜져 있으면 가짜 주소로 메일을 보내려다 가입이 막힙니다.
  - **무료 플랜 7일 미사용 시 일시정지**와 복구 방법
  - 무료 플랜에는 백업 다운로드가 없다는 점 → 앱의 **"전체 백업 내보내기 / 가져오기"** 기능으로 보완했습니다.
  - GitHub Pages(무료)는 **저장소를 공개**해야 한다는 점. 공개해도 안전한 이유: `anon` 키는 원래 공개용이고, 데이터는 로그인과 DB 함수 권한으로 보호됩니다.
  - 원본 자료에는 실명이 들어 있으므로 **`_original/` 폴더는 GitHub에 올리지 않습니다**(`.gitignore` 처리).

## 8. 이번 코드에서 하지 않은 것(남은 과제)

- 실제 Supabase 프로젝트에 적용해 보는 시험은 **사용자가 프로젝트를 만든 뒤에 해야 하므로 아직 하지 않았습니다**. 설치 가이드 7단계의 확인 목록으로 함께 점검합니다.
- 항목의 등록자(`createdBy`)는 화면이 기록하며, 서버가 강제하지 않습니다. 가족용이라 허용했습니다.
- 계정을 삭제하기 전에는 그 사람이 유일한 Owner인 목록의 소유권을 먼저 넘겨야 합니다(가이드에 절차 기재).
